# Privacy and Personal Data

This document describes how the `steam-workshop-update` GitHub Action handles personal data when updating a mod on the Steam Workshop. It covers the application behaviour and verified integrations. The action runs on GitHub Actions runners (GitHub-hosted or self-hosted); the runner operator controls the execution environment.

## 🔎 What This Document Covers

This document describes how `steam-workshop-update` at https://github.com/hmlendea/steam-workshop-update handles personal data. It covers the application behaviour and verified integrations described below. Where the software runs on self-hosted runners, the runner operator may have separate responsibilities described below.

## 📥 Data We Handle

### Data Provided to the Application

- Steam account username (`STEAM_USERNAME`) — provided via GitHub Actions secrets by the workflow author.
- Steam account password (`STEAM_PASSWORD`) — provided via GitHub Actions secrets by the workflow author.
- Steam 2FA seed (`STEAM_2FASEED`) — optional, provided via GitHub Actions secrets by the workflow author; a standard TOTP seed (not the Steam Guard base64 secret).
- Workshop update metadata: Steam App ID (`appid`), Workshop Item ID (`itemid`), mod content path (`path`), and optional changenote (`changenote`) — provided as workflow inputs; these are not personal data.

### Data Generated or Collected by the Application

- Authentication tokens and session data generated by `steamcmd` during login to Steam.
- Time-based one-time passwords generated from the `STEAM_2FASEED` by the bundled `steam-totp` tool.
- Steam client logs (`stderr.txt`, `workshop_log.txt`) produced by `steamcmd` in `/home/steam/Steam/logs/`, which may contain fragments of authentication traffic or error details.
- A temporary `workshop.vdf` file written to `/home/steam/workshop.vdf` containing the `appid`, `contentfolder`, `changenote`, and `publishedfileid`; this file does not contain credentials.

### Data Received from Integrations

- No personal data is received from third-party integrations. The action communicates only with Steam (Valve) servers for authentication and workshop upload.

## 🧭 Processing and Use

The application processes the data described above for these verified functions:
- Authenticate to Steam using the provided username, password, and optional 2FA code — Steam credentials (`STEAM_USERNAME`, `STEAM_PASSWORD`, `STEAM_2FASEED`).
- Generate a time-based one-time password from the 2FA seed when `STEAM_2FASEED` is supplied — `STEAM_2FASEED`.
- Upload the specified workshop item content to the Steam Workshop via `steamcmd` — workshop metadata (`appid`, `itemid`, `path`, `changenote`).
- Retry the upload up to three times on failure — same data as above.
- Emit logs for debugging failed attempts — Steam client logs.

## 🗄️ Storage, Retention, and Deletion

- Credentials (`STEAM_USERNAME`, `STEAM_PASSWORD`, `STEAM_2FASEED`) exist only as environment variables in the runner process for the duration of the job. They are not written to disk by the action.
- The `workshop.vdf` file is created in the container filesystem at `/home/steam/workshop.vdf` and persists only for the job duration.
- Steam client logs are written to `/home/steam/Steam/logs/` inside the container and persist only for the job duration.
- GitHub Actions retains workflow run logs (including any `echo` output from the entrypoint) according to the repository's log retention settings, controlled by the repository owner or organisation.
- For self-hosted runners, the runner operator controls the underlying host storage, backups, and log retention.
- The action does not implement independent data deletion; cleanup occurs when the job container is removed.

## 🔗 External Processing and Integrations

| Service or integration | Purpose | Data involved | Configuration or documentation |
|-----------------------|---------|---------------|--------------------------------|
| Steam (Valve) | Authenticate the Steam account and upload the workshop item | `STEAM_USERNAME`, `STEAM_PASSWORD`, `STEAM_2FASEED` (via 2FA code), `appid`, `itemid`, `path`, `changenote` | https://partner.steamgames.com/doc/features/workshop |
| GitHub Actions | Execute the workflow job and provide secrets/runtime | All inputs and secrets passed to the action | https://docs.github.com/en/actions |

The action has no other built-in external data transfers.

## ⚙️ User Controls and Requests

The following documented controls or request procedures are available:
- Rotate or revoke `STEAM_USERNAME`, `STEAM_PASSWORD`, and `STEAM_2FASEED` in the repository or organisation secrets settings — GitHub Actions secrets management.
- Remove the workflow step or change inputs to stop future executions — workflow configuration.
- Delete workflow run logs from the GitHub UI or via the REST API — GitHub Actions log retention controls.
- For self-hosted runners, the runner operator controls access to the runner host, container runtime, and any persisted logs or artefacts.

## 🌍 International Transfers

- Steam (Valve) servers are operated from the United States. Authentication and workshop upload traffic is transmitted to Valve's infrastructure regardless of runner location.
- GitHub Actions runners (GitHub-hosted) operate in Microsoft Azure regions selected by GitHub; self-hosted runner location is determined by the runner operator.
- No other cross-border data transfers are performed by the action.

## 🛡️ Data Protection and Security

- Credentials are supplied exclusively through GitHub Actions secrets, which are encrypted at rest and masked in workflow logs.
- The entrypoint script does not write credentials to files or stdout; it passes them directly to `steamcmd` via command-line arguments.
- The `steam-totp` tool runs locally in the container to generate 2FA codes; the seed never leaves the container.
- Steam client logs may contain sensitive fragments; they are printed to stdout only on failure (after three retries) and are subject to GitHub Actions log retention.
- For self-hosted runners, the operator is responsible for runner host hardening, container runtime security, network exposure, secret handling in the runner environment, and log protection.
- The original maintainers are not responsible for changes, modifications, or privacy issues introduced by downstream forks.
